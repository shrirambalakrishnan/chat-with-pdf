# Chat with PDF

Upload your PDF and chat with it!

Answers to your questions will be grounded to the document you have uploaded!

## Setup

### Prerequisites

- Node **v26.2.0** and npm **11.13.0** (enforced — `npm install` fails on other versions)
- A GCP project with:
  - a Cloud Storage bucket
  - a Firestore database
  - a service account with object read/write/delete on the bucket and Firestore read/write
  - the Vertex AI API enabled, and the `Vertex AI User` role (`roles/aiplatform.user`) on the service
    account, to call the embedding model:

    ```sh
    gcloud services enable aiplatform.googleapis.com --project <project-id>
    gcloud projects add-iam-policy-binding <project-id> \
      --member serviceAccount:<service-account-email> \
      --role roles/aiplatform.user
    ```

```sh
nvm use        # picks v26.2.0 from .nvmrc
npm install
```

### Service account key

Download a JSON key for the service account from the GCP console and save it at the repo root as
`service-account-key.json`. This file is gitignored — never commit it.
`service-account-key.example.json` shows the expected shape.

### Environment variables

Copy `.env.example` to `.env` and fill in every value:

| Variable | Description |
| --- | --- |
| `GCP_PROJECT_ID` | GCP project id |
| `GCS_BUCKET_NAME` | Cloud Storage bucket name |
| `FIRESTORE_DATABASE_ID` | Firestore database id (`(default)` for the default database) |
| `GOOGLE_APPLICATION_CREDENTIALS` | Path to the service account key file, e.g. `./service-account-key.json` |
| `VERTEX_LOCATION` | Vertex AI region for the embedding model, e.g. `us-central1` |
| `EMBEDDING_MODEL` | Embedding model, `gemini-embedding-001` |
| `EMBEDDING_DIMENSIONS` | Embedding size, `768`. At most 2048 (Firestore's vector limit) |
| `PORT` | Optional, defaults to `3000` |

The service refuses to start if any required variable is missing, and names the missing ones.

### Run

```sh
npm start      # run the server
npm run dev    # run with auto-restart on file changes
```

Check it is up:

```sh
curl http://localhost:3000/health   # {"status":"ok"}
```

## Data model

### `users` collection

| Field | Type | Notes |
| --- | --- | --- |
| document id | string | Fixed for the seed user (from the seed config file), auto-generated for real users later. Not duplicated as a field. |
| `name` | string | |
| `email` | string | |
| `createdAt` | timestamp | Set by the server when the document is created |

### `documents` collection

Document ids are auto-generated by Firestore.

| Field | Type | Notes |
| --- | --- | --- |
| `ownerId` | string | id of the user in `users` |
| `filename` | string | original name supplied by the client |
| `contentType` | string | `application/pdf` |
| `size` | number | bytes, as declared by the client |
| `gcsUri` | string | `gs://{bucket}/documents/{documentId}.pdf` (the bucket is private) |
| `status` | string | `pending_upload` → `uploaded` → `processing` → `ready`, or `failed` |
| `error` | string or null | reason, when status is `failed` |
| `createdAt` | timestamp | server time |
| `updatedAt` | timestamp | server time |

### `chunks` collection

Written by RAG ingestion. One document per chunk of a PDF's text. Document id is
`{documentId}_{index}`, so re-ingesting a PDF overwrites its chunks by id instead of duplicating them.

| Field | Type | Notes |
| --- | --- | --- |
| `ownerId` | string | id of the user in `users` |
| `documentId` | string | id of the record in `documents` |
| `index` | number | position of the chunk in the document, from 0 |
| `text` | string | chunk text, about 200 words |
| `pageStart` | number | first page the chunk covers, from 1 |
| `pageEnd` | number | last page the chunk covers |
| `embedding` | vector | `EMBEDDING_DIMENSIONS` numbers, as returned by the model |
| `createdAt` | timestamp | server time |

## RAG ingestion

`src/rag/` turns a PDF into chunks that can be searched by meaning. It is a self-contained module: it
knows nothing about HTTP, the `documents` collection or document status, and reads no environment
variables. Its clients and settings are passed in; `src/lib/rag.js` builds them from config.

### Pipeline

```
PDF bytes ──▶ extract pages ──▶ chunk ──▶ embed ──▶ vector store
              (text per page)   (200 words,   (gemini-embedding-001,  (Firestore chunks
                                 30 overlap)   RETRIEVAL_DOCUMENT)     collection)
```

1. **Extract** the text layer page by page (`unpdf`). PDFs are assumed to have one; a PDF with no
   text at all is rejected.
2. **Chunk** into windows of 200 words. Each chunk repeats the last 30 words of the previous one, so
   an idea cut at a chunk edge still appears whole in the next chunk, and words are never cut in
   half. Chunks may cross page breaks and record `pageStart` / `pageEnd` (the pages of their first
   and last word) for citations.
3. **Embed** each chunk with task type `RETRIEVAL_DOCUMENT`. Questions must later be embedded with
   `RETRIEVAL_QUERY`, the same model and the same dimensions, or they will not match.
4. **Store** the chunks with their embeddings. Chunks of the same document stored earlier are
   overwritten by their deterministic id.

| File | Role |
| --- | --- |
| `index.js` | The module's public API |
| `ingestPdf.js` | Runs the pipeline for one PDF |
| `extractPages.js` | Text per page |
| `chunkPages.js` | Overlapping, page-aware word windows |
| `embedder.js` | Gemini embedder, one request per chunk, in order |
| `vectorStores/firestore.js` | Vector store on Firestore native vector search |

```js
const { ingestPdf } = require('./src/rag');
const { embedder, vectorStore } = require('./src/lib/rag');

await ingestPdf(pdfBuffer, { ownerId, documentId }, { embedder, vectorStore });
// → { pageCount, chunkCount }
```

### Embedding requests

Gemini embedding models on Vertex AI take **one text per request** (other Vertex embedding models
take up to 250), and at most 2048 tokens per text; a 200-word chunk is about 260 tokens. So a PDF
costs one request per chunk: a 300-page PDF is a few hundred requests. They run one after another,
with no retries yet, so a rate limit (`429`) or transient error fails the ingestion.

### Swapping the vector store

Ingestion only calls the vector store contract, documented in `vectorStores/firestore.js`:

| Method | Purpose |
| --- | --- |
| `upsert(records)` | Store chunks with their embeddings, keyed by chunk id |

`query` (nearest chunks) is added to the contract with retrieval (#3).

To use Vertex AI Vector Search or Pinecone instead, add a file in `vectorStores/` that implements the
contract (using the chunk id as the vector id, and `ownerId` / `documentId` as filters) and pass it
from `src/lib/rag.js`. Nothing else changes.

The Firestore vector index on `chunks.embedding` is not needed to write chunks, only to query them, so
it is set up with retrieval.

### Try it on a local PDF

With `.env` and the key file in place:

```sh
npm run rag:ingest -- report.pdf seed-user test-doc
# Ingested report.pdf: <pages> pages, <n> chunks in <seconds>s (chunks/test-doc_0 to chunks/test-doc_<n-1>)
```

The ids are stored on the chunks as given; they do not have to match an existing user or document.
Use a new `documentId` when trying a different PDF: re-running overwrites chunks by id but does not
delete any, so leftover chunks from an earlier, longer PDF would stay.

## Seed user

Until auth exists, every document belongs to a single seed user. Its `id`, `name` and `email` live in
`scripts/seed-user/seed-user.json`. That file is for seeding only — application code reads users from
Firestore, never from this file.

With `.env` and the key file in place, create the seed user:

```sh
npm run seed:user
```

This creates `users/{id}` using the `id` from the config file as the document id. It is safe to re-run:
if the user already exists it is left unchanged.

## API

Until auth exists, the caller is identified by the `X-User-Id` header, which must match a document in
the `users` collection (e.g. the seed user).

### `POST /documents`

Asks for permission to upload one PDF. Creates a `documents` record with status `pending_upload` and
returns a signed URL; the client then uploads the file directly to Cloud Storage.

Request body:

| Field | Type | Rules |
| --- | --- | --- |
| `filename` | string | required |
| `contentType` | string | must be `application/pdf` |
| `size` | number | bytes, 1 to 20 MB (20971520) |

```sh
curl -X POST http://localhost:3000/documents \
  -H 'Content-Type: application/json' \
  -H 'X-User-Id: seed-user' \
  -d '{"filename": "report.pdf", "contentType": "application/pdf", "size": 123456}'
```

Response `201`:

```json
{
  "documentId": "AbC123...",
  "uploadUrl": "https://storage.googleapis.com/<bucket>/documents/AbC123....pdf?X-Goog-Algorithm=...",
  "uploadHeaders": {
    "Content-Type": "application/pdf",
    "x-goog-content-length-range": "1,20971520"
  },
  "expiresAt": "2026-01-01T00:15:00.000Z"
}
```

Errors:

| Status | When |
| --- | --- |
| `400` | missing or invalid body field, `contentType` is not `application/pdf`, or `size` is zero or over 20 MB |
| `401` | `X-User-Id` header missing |
| `403` | `X-User-Id` does not match a user |

#### Uploading to the signed URL

`PUT` the file to `uploadUrl` within 15 minutes, sending every header in `uploadHeaders` exactly as
returned. Cloud Storage rejects the upload if the content type differs or the file is over 20 MB.

```sh
curl -X PUT "<uploadUrl>" \
  -H 'Content-Type: application/pdf' \
  -H 'x-goog-content-length-range: 1,20971520' \
  --upload-file report.pdf
```

After the `PUT` succeeds, call `POST /documents/:id/complete`.

### `POST /documents/:id/complete`

Tells the service the upload has finished. The service verifies the stored file and updates the
document's status. No request body.

The stored file must:

- exist at the document's `gcsUri`
- be larger than zero and at most 20 MB
- have content type `application/pdf`
- start with the PDF signature `%PDF-`

| Case | Status | Effect on the record |
| --- | --- | --- |
| File is present and valid | `200`, returns the document | status → `uploaded`, `size` → actual object size |
| File is present but invalid | `422`, returns the reason | status → `failed`, `error` set, object deleted from the bucket |
| File is not in the bucket yet | `409` | unchanged (`pending_upload`): upload, then retry |
| Document is already `uploaded` or later | `200`, returns the document | unchanged |
| Document is already `failed` | `409` | unchanged: start again with `POST /documents` |
| `X-User-Id` header missing | `401` | unchanged |
| `X-User-Id` is not a user, or not the document's owner | `403` | unchanged |
| No document with that id | `404` | none |

```sh
curl -X POST http://localhost:3000/documents/<documentId>/complete \
  -H 'X-User-Id: seed-user'
```

Once a document is `uploaded`, it is picked up from Firestore by the (future) processing service.

Upload completion lives in `src/uploads/`, separate from the rest of the API:

| File | Role |
| --- | --- |
| `completeUpload.js` | Core: verifies the stored file and settles a `pending_upload` document. Safe to call repeatedly or concurrently. No HTTP or auth. |
| `verifyUpload.js` | The checks on the stored file, used by the core |
| `completeRoute.js` | This endpoint: checks the user and ownership, calls the core, maps the outcome to a status code. Mounted with one line in `src/app.js`. |

Another way of detecting completion (e.g. Cloud Storage events via Pub/Sub, #9) should call
`completeUpload` from its own entry point. Removing this endpoint means deleting `completeRoute.js`
and its mount line.

### Walkthrough: upload a PDF end to end

Requires [`jq`](https://jqlang.org/). With the server running and the seed user created:

```sh
FILE=report.pdf
SIZE=$(wc -c < "$FILE" | tr -d ' ')

# 1. Ask for a signed upload URL
RESPONSE=$(curl -s -X POST http://localhost:3000/documents \
  -H 'Content-Type: application/json' \
  -H 'X-User-Id: seed-user' \
  -d "{\"filename\": \"$FILE\", \"contentType\": \"application/pdf\", \"size\": $SIZE}")
DOCUMENT_ID=$(echo "$RESPONSE" | jq -r .documentId)
UPLOAD_URL=$(echo "$RESPONSE" | jq -r .uploadUrl)

# 2. Upload the file straight to Cloud Storage
curl -X PUT "$UPLOAD_URL" \
  -H 'Content-Type: application/pdf' \
  -H 'x-goog-content-length-range: 1,20971520' \
  --upload-file "$FILE"

# 3. Confirm the upload; status becomes "uploaded"
curl -X POST "http://localhost:3000/documents/$DOCUMENT_ID/complete" \
  -H 'X-User-Id: seed-user'
```
